本页重点

全链路总图

蓝：HTTP/消息 · 紫：调度 · 橙：显存 · 绿：GPU · 粉：TP · 青：Speculative。实线是主要数据路径，虚线通常表示反馈、条件或跨模块联系。查看时请从 Client POST 开始，一直跟到 Detokenizer → SSE。

请求与进程

用户请求经 FastAPI → TokenizeMsg → Tokenizer → UserMsg → Scheduler；返回是 DetokenizeMsg → Detokenizer → UserReply → ack_map/event_map。客户端断开后是协作式 Abort，GPU 已提交的工作并不立即被强制杀掉。

连续批处理

实现中的 `_schedule_next_batch` 优先尝试 prefill，否则 decode。PrefillAdder 检查 request slot、KV 容量和本轮 token_budget；长 prompt 可以 Chunked Prefill，中间 chunk 不采样、不进入 Decode。

存储层：3 个结构

KV Pool 是 GPU 实际 K/V；page_table 每行对应一个活动 Req，表项存物理 token slot；Radix Tree 将 token 前缀映射到共享的 KV slot 范围。命中后要 lock；结束后可插入完整前缀并释放不可复用页。

神经网络与 TP

每一层将新增 K/V 写入 pool，并用 page table 对历史 KV 做因果 Attention。Column-Parallel 对输出/head 方向切分；Row-Parallel 的局部输出需要通信合并。Prefill logits 产生第一个输出 token，但这个 token 自身的 K/V 要到下一轮 Decode 才计算。

投机解码不是 mini 基线

第 10 章代码引用的是正式 SGLang 的固定版本，不要误以为 mini-sglang 原始基线自带该模块。先 Draft k 个 token，再 Target 一次 Verify，首次拒绝就停止、纠正，全部接受则可 Bonus；随机版要使用正残差修正，才能保持目标采样分布。

A / B / C 是教学例子

这个标签展示请求独立进出 batch 的原则，并非源代码必然的逐轮调度序列。实际哪个 prefill 或 decode 在某轮运行由 budget、资源、排队顺序和配置共同决定。
